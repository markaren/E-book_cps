## 1. Choose the QoS

*Practises: [ROS2 Concepts](ros2_concepts.md) (QoS), [Part 4 QoS](../Chapter4/exercises.md)*

Your simulated car publishes a **lidar scan at 20 Hz** on `/scan`. The subscriber that consumes it — an obstacle detector — is **slow**: some scans take longer than 50 ms to process. Choose the DDS **reliability** and **history/depth** QoS for this topic, and justify it. What goes wrong with the *opposite* choice?

> Hint: ask the Part 4 question — is a lost scan acceptable? A fresh scan arrives every 50 ms. What does `RELIABLE` + a deep queue do when the subscriber falls behind?

??? success "Show discussion"

    <div class="spoiler" markdown title="Click to reveal">

    **Best-effort, keep-last with a small depth (e.g. 1–5).** Lidar is *fresh-or-nothing* state: a scan that is two frames old is useless when a newer one exists, so you never want to retransmit a lost one. `BEST_EFFORT` says "don't bother re-sending dropped samples", and `KEEP_LAST(1)` (or a small depth) means the subscriber, when it finally gets a turn, reads the **latest** scan and the stale ones have been discarded.

    The opposite choice — **`RELIABLE` with a deep or `KEEP_ALL` history** — is the trap. When the subscriber falls behind, reliable delivery + a deep queue means the middleware **buffers every** scan and keeps re-delivering old ones. The detector now works through an ever-growing backlog of *stale* scans, falling further behind on every cycle — latency grows without bound and it acts on obstacles that have moved. This is the same "freshness over completeness" judgement as the [50 Hz telemetry in Part 4](../Chapter4/exercises.md): high-rate loss-tolerant data wants low reliability and a shallow queue. (Reliability + depth is exactly right for a *different* topic — a one-off map or a command — where every message must arrive.)

    </div>

## 2. Port an MQTT design to ROS2

*Practises: [ROS2 Concepts](ros2_concepts.md), [MQTT & RPC](../Chapter4/mqtt_rpc.md)*

In [Part 4's design exercise](../Chapter4/exercises.md) you designed a fleet's comms with **MQTT** (robots publish `robot/<id>/telemetry` at 50 Hz; the operator sends must-arrive commands). Re-express that design in **ROS2 terms**. For each piece, name the ROS2 equivalent and say what changes and what doesn't: the telemetry channel, the command channel, the broker, the QoS, and the message format.

> Hint: walk the [one-table translation](ros2_concepts.md). Which MQTT pieces map one-to-one? Which one *disappears*? Is the "must-arrive command" better a topic or a service?

??? success "Show discussion"

    <div class="spoiler" markdown title="Click to reveal">

    - **Telemetry topic.** `robot/<id>/telemetry` → a ROS2 **topic** like `/robot_<id>/telemetry`, published at 50 Hz. Pub/sub is unchanged; the operator dashboard subscribes. QoS: **best-effort, keep-last small** — the direct analogue of MQTT **QoS 0** for fresh-or-nothing state.
    - **The broker disappears.** MQTT needed a running **Mosquitto** broker; ROS2's **DDS discovers** nodes peer-to-peer, so there is **no broker to run or to fail**. That is the single biggest structural change.
    - **The command.** "Must take effect" → either a **reliable topic** (`RELIABLE` QoS, the MQTT QoS 1/2 analogue) **or**, better, a **service** — request/response gives you a *confirmation reply* that the robot received and accepted the command, which fire-and-forget pub/sub does not. If the command is long-running ("return home"), an **action** is better still: feedback + the ability to cancel.
    - **Message format.** Ad-hoc [JSON on MQTT](../Chapter4/serialization.md) → a **typed `.msg`** (reuse `sensor_msgs`/`geometry_msgs` where one fits) generated by the IDL codegen, so both ends share the schema — the [`.proto`→`.msg`](ros2_concepts.md) shift.

    What *doesn't* change is the underlying judgement: telemetry is many-to-many, frequent, loss-tolerant → pub/sub with low QoS; the command is point-to-point and must-arrive → reliable delivery with confirmation. ROS2 gives the same decisions cleaner names and a brokerless graph.

    </div>

## 3. Talker and listener in the workspace

*Practises: [ROS2 Workspace](ros2_workspace.md), [ROS2 on Windows](ros2_windows.md)*

In your [RoboStack workspace](ros2_windows.md), create two packages — `talker` and `listener` — with the minimal [rclcpp publisher and subscriber](ros2_concepts.md). Build them with colcon, run both, and confirm messages flow. Then observe the topic **from outside** with the command-line tools.

> Hint: run everything inside `pixi shell -e jazzy`. Build with `colcon build --base-paths src --merge-install`, then source the workspace's install so `ros2 run` finds your packages. Use three terminals (talker, listener, and one for `ros2 topic`).

??? success "Show expected output and why"

    <div class="spoiler" markdown title="Click to reveal">

    With `ros2 run talker talker` in one terminal and `ros2 run listener listener` in another, the listener prints each message the talker sends:

    ```
    [INFO] [listener]: I heard: 'hello 0'
    [INFO] [listener]: I heard: 'hello 1'
    [INFO] [listener]: I heard: 'hello 2'
    ```

    And a third terminal watching the topic directly:

    ```
    $ ros2 topic list
    /chatter
    /parameter_events
    /rosout

    $ ros2 topic echo /chatter
    data: 'hello 3'
    ---
    data: 'hello 4'
    ---
    ```

    Two things are worth registering. First, **you started no broker** — the two nodes found each other purely through [DDS discovery](ros2_concepts.md), which is the brokerless difference from [MQTT](../Chapter4/mqtt_rpc.md) made concrete. Second, `ros2 topic echo` subscribed to `/chatter` as a *third* participant with zero code, printing the live stream — this is the system-wide `print`-debugging you will lean on constantly, and the first thing to reach for when a subscriber is silent (check the topic really carries data, then check the [QoS matches](ros2_concepts.md)). Once this works, swap the talker's dummy string for a reading from your [simulator](../Chapter6/virtual_environments.md) and echo *that*.

    </div>

## 4. Where does the callback run?

*Practises: [ROS2 Concepts](ros2_concepts.md) (executors), [Sharing Data](../Chapter2/sharing_data.md)*

A single node has **two** subscriptions — one on `/scan`, one on `/command` — and both callbacks update a shared `RobotState` object (the scan callback writes the latest obstacle map; the command callback writes the current goal). A classmate says "it's one node, so it's single-threaded, no locking needed." Are they right? Explain in terms of ROS2 **executors**, and say when the answer changes.

> Hint: what runs your callbacks? How many threads does `rclcpp::spin` use by default versus a `MultiThreadedExecutor`? Recall the [AI-generated concurrency trap](../using_ai.md) — "it ran fine once" is not proof.

??? success "Show discussion"

    <div class="spoiler" markdown title="Click to reveal">

    **It depends on the executor — so the safe answer is "don't rely on it being single-threaded."** The default `rclcpp::spin` uses a **single-threaded executor**: it runs callbacks one at a time on one thread, so with the default executor the two callbacks *cannot* run concurrently and the shared `RobotState` is not racing — the classmate is accidentally right, *for that configuration only*.

    But the moment someone switches to a **`MultiThreadedExecutor`** (common, and often added later for throughput), callbacks can run on **different threads at the same time**, and the scan callback writing the obstacle map while the command callback reads state is a textbook [data race](../Chapter2/sharing_data.md) — exactly the Part 2 hazard. The correctness of the code now silently depends on an executor choice made elsewhere. The disciplined answer: treat callbacks as potentially concurrent and **guard the shared state** ([a mutex](../Chapter2/sharing_data.md), or route both callbacks' work through a single [queue/mailbox](../Chapter2/condition_variables.md)), or explicitly pin them to a [callback group](ros2_concepts.md) that serialises them. "It worked with the single-threaded executor" is precisely the [runs-fine-once illusion](../using_ai.md) that hides concurrency bugs — the executor is the concurrency boundary, and Part 2's rules live there.

    </div>
